# 调度层导读（`schedule/`）

所有「到点要发生的事」都在这层。核心链路：

```
排程器（各 Planner）──排──► ReminderScheduler ──► 系统 AlarmManager
                                                        │ 到点
                                                        ▼
                                              ReminderReceiver（按 requestCode 分发）
                                                        │
                                                        ▼
                                    通知层发通知 / 续排下一个 / 查库判断要不要发
```

## ReminderReason.kt —— requestCode 体系（本层的地基）

每类提醒占一个编号段，编号同时是 PendingIntent 的 requestCode 与接收器的分发依据：

| 段 | 用途 |
|---|---|
| 1001-1003 | 三餐询问 |
| 2001 | 背单词循环 |
| 3001/3002 | 晚间规划首次 / 二次 |
| 4001 | 测试待办 |
| 4100 + 任务 id | 真实待办（id 是数据库自增，**理论上无上限**） |
| 200000-200009 | 起床唤醒（固定码块，最多 10 声） |
| 200101-200104 | 起床调试模拟（独立码段） |

两条血泪教训写进了注释，改这块前必读：

1. **段与段必须互不相交**：早期唤醒用 5000 段，整段落进了待办段的 4100..104099，被待办分支吞掉——唤醒闹钟准点触发却按不存在的任务 id 静默跳过，起床通知从未发出（排查记录见 env-pitfalls #18）。所以待办段头大留增长空间，唤醒段整体搬到 200000。
2. **同码即同一闹钟**：AlarmManager 靠 (intent + requestCode) 识别闹钟，两个调度共用一个码就是互相覆盖。调试模拟因此独占一段，绝不碰真实计划的码。

## ReminderScheduler.kt —— AlarmManager 唯一封装

全应用的闹钟都从这两个方法进出（`schedule` / `cancel`）：

- `setExactAndAllowWhileIdle`：精确闹钟，应用被杀、设备 Doze 打盹都照样准点触发
- Android 12+ 未授「精确闹钟」权限时自动退化 `setAndAllowWhileIdle`（仍会触发，时刻可能漂移几分钟）——**降级而不是失效**，用户没开权限时应用不至于哑掉
- `canScheduleExact` 供设置页显示权限提示

## ReminderReceiver.kt —— 到点分发中枢

闹钟触发的广播接收器。两个关键设计：

1. **`goAsync()` + 协程**：广播的 `onReceive` 在主线程且必须快进快出，但这里要查数据库——`goAsync()` 拿到挂起结果对象，扔到 IO 协程里干活，`finally { finish() }` 保证异步收尾后才算广播结束（不这样做，进程可能在查库途中被杀）
2. **`when (requestCode)` 分发，窄区间在前**：起床/调试的窄段排在待办宽段前面——when 从上到下匹配，宽段在前会吞掉后面的窄段（教训同上）

各分支的逻辑（都以「先判断该不该发，再发/续排」为骨架）：

- **三餐**：查当天该餐别记录数，0 条才发询问通知（已记录静默）；随后 `DailyPlanner.rescheduleMeals` 把闹钟滚到明天
- **背单词**：未确认「今日已背」才发提醒，随后滚到下一锚点
- **规划首次**：先动态排今晚 23:00 的二次提醒（若还没过 23:00），再查今晚是否已规划决定发不发；**二次提醒**：仍未规划才再发一次
- **待办**：按 id 反查任务，存在且未完成才发
- **起床**：按码段算第几声、从 DataStore 存档读总数，末声走持续震动分支（见通知层）
- **调试模拟**：独立段，直接发对应样式的通知

每条到点都会打一行 `fired requestCode=...` 日志——排查「闹钟到底响没响」靠它。

## DailyPlanner.kt —— 每日提醒排程

三餐与晚间规划的「排到下一个触发点」逻辑，幂等可重入：

- `scheduleNextDaily`：算「今天该时刻」，已过则排明天同时刻。**没有用系统闹钟的 repeat 机制**，而是每次到点触发后由接收器重新排下一个——简单、可随时改时刻、无重复排程风险
- `rescheduleTodoTasks`：待办自愈——把所有「未完成且提醒时刻未过」的任务重排，开机与每次应用启动时调用

## VocabPlanner.kt —— 背单词锚点循环

「10:00 起每 90 分钟，到 23:00 为止」的循环，实现是**锚点制**而不是排队：

- `nextAnchorAfter(from)`：纯函数，算 from 之后的下一个锚点；当天窗口耗尽返回明天 10:00。逻辑就是一个 while：从今天 10:00 起不断 +90 分钟直到晚于 from，中途超过 23:00 就跳明天
- 每次闹钟到点 → 发提醒 → `reschedule` 排下一锚点；确认「今日已背」→ 直接排明天 10:00
- **完成状态按日期存 DataStore**（`vocabDoneDate`），次日自动失效——不需要任何「零点重置」任务

## WakePlanner.kt —— 起床渐进唤醒（双保险的应用侧）

「双保险」方案：系统时钟闹钟做叫醒主力（用户手动开，应用只引导跳转），应用排 N 声渐进震动做保底。本文件管应用这半边：

- `generateWakeTimes(date, morningClass, count=4)`：前 N-1 声在随机窗口（早八 07:30-07:59 / 早十 09:15-09:44）取**互不重复**的随机分钟（`mutableSet` 去重 + 排序），末声固定 08:00 / 09:45（上课前 30 分钟）
- `plan()`：**撤旧排新**——先 `cancelAll` 整个码块再排 N 声，然后存档 DataStore。每天重新规划也永远只有 N 条闹钟，零积累
- `cancel()` / `cancelAll()`：无课或改选时清闹钟清存档
- `rescheduleFromStore()`：自愈——从存档读时刻重排（已过去的跳过）。开机广播与应用启动都会调它

「去时钟开闹钟」的引导入口在界面层（PlanScreen / RemindScreen），跳转封装在工具层（ClockLinker）。

## SystemAlarmSetter.kt —— SET_ALARM 写系统时钟（停用备用）

最早期的方案：用安卓标准的 SET_ALARM Intent 让系统时钟应用代建起床闹钟。真机实测发现两个致命问题后停用（保留代码备用）：

- 公开 API **读不到也删不掉**时钟里已有的闹钟，每天自动新建必然堆积
- 只有一个闹钟不够叫醒

详见 goal.md 的决策记录。

## BootReceiver.kt —— 开机自愈

监听 `BOOT_COMPLETED` 广播，把五类排程器全部重跑一遍——安卓重启会清空所有应用闹钟，这里是可靠性的第一道保险（第二道是每次应用启动时 DailyControlApp 的同样调用，见 util-and-entry.md）。依赖 HyperOS 的「自启动」权限，真机已实测生效。
