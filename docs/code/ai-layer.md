# AI 协调层 ai/（0.4.0 第四阶段第一批 · 0.4.1 追问机制）

> 全应用**唯一的网络出口**。六个文件：一个 HTTP 客户端、三个纯逻辑组装/拆解器、一个数据契约、一个编排器。
> 设计总纲见 [../architecture.md](../architecture.md)；本篇按文件下钻。

## 总体数据流

```
凌晨4:00闹钟 / 启动自愈 / AI页懒检查 / 「立即生成」按钮
        │  全部只调 AiReportGenerator 这一个入口（内部单飞锁，并发触发自动去重）
        ▼
AiDataSummarizer ──近30天统计概要──┐
                                  ├─► AiPromptBuilder ──提示词──► AiClient ──HTTPS──► 用户配置的接口
DAO 明细查询 ───昨日/缺口/30天明细──┘                                   │
                                                                      ▼
                        AiReport ◄── AiReportParser ◄── 返回正文（JSON）
                        （Room v5 落库，14 天滚动清理）
```

## AiClient.kt —— OpenAI 兼容 HTTP 客户端

- **为什么用 HttpURLConnection 而不是 OkHttp**：每天仅一次请求，任何第三方网络库都是为一次调用背上依赖与镜像拉取风险；平台自带库完全够用。
- `ChatMessage(role, content)`：OpenAI 消息格式的最小封装（system 设定角色 / user 携带数据）。
- `CallResult` 三态：`Success(正文)` / `HttpError(状态码, 可读原因)` / `NetworkError(可读原因)`。状态码映射：401 Key 无效、402 欠费、404 地址不对、429 受限、5xx 服务商故障——这些就是「中断补交」无需专门逻辑的原因：所有失败殊途同归为「不记账」。
- `chat()`：默认带 `response_format: json_object` + `temperature 0.4` 请求稳定 JSON；收到 400（个别兼容商不认该参数）自动去掉参数原样重试一次。
- `testConnection()`：发一条最小消息验证三要素整条链路，设置页「测试连接」按钮用。
- 端点拼装：用户填到 `/v1` 为止的 Base URL 自动补 `/chat/completions`；直接粘完整端点也能识别。
- 超时：连接 15 秒、读取 120 秒（大模型生成一份报告需要几十秒）。
- **安全**：Key 只出现在 `Authorization: Bearer` 请求头；本文件无任何日志输出。

## AiDataSummarizer.kt —— 近 30 天统计概要

纯函数：明细列表 → 中文键 JSONObject。统计内容：三餐规律度（各餐覆盖天数占比）、高频食物 Top10（食材文本按顿号/逗号拆词）、常吃营养品与成分剂量频次、运动类型/强度分布与覆盖天数。**为什么程序算而不用 AI 数**：又快又稳不出错、token 成本恒定（每天约 700 token）、隐私面最小。

## AiPromptBuilder.kt —— 提示词组装

- system 提示词：**应用内「提示词定制」保存的非空文本会整体覆盖内置默认**（设置 → AI 接口 → 提示词定制（高级）；定制随备份导出，一键恢复默认）。内置默认（`buildDefaultSystemText()`）为：营养学顾问角色（以《中国居民膳食指南（2022）》为参照、无明显过量不建议节食）+ 严格输出 JSON 约定：summary 为 **2~4 个关键要点**（每条 15 字内短语、分号分隔、共 60 字内）；分析各 120 字内；建议 3~5 条且**使命是帮助用户养成可长期坚持的生活习惯**——以值得坚持/培养/调整的长期习惯为主（依据近 90 天长期概要）、单日显著异常的即时纠正为辅（提醒级）、单日小波动不给建议；每条遵循**「先做什么、再为什么」**——`headline` 约 15 字行动摘要、`detail` 80 字内执行细节（份量/时机/营养品剂型）、`basis` 60 字内依据（数据事实 + 指南推荐量）、`level` 两档；营养缺口给**双层补充指引**（优先食物来源；适合营养品高效补充的同时给剂型与参考剂量区间，注明「以产品说明或医嘱为准」，禁止指定品牌）；追问 `questions` 审慎四原则（档案已有的不问、长期不变的只问一次、短期波动确有需要才问、无必要空数组）。
- **追问约定（0.4.1）**：`questions` 为 AI 向用户提的问题 `[{topic,text,type}]`，type ∈ profile（档案型，长期有效）/oneoff（一次性）；提问审慎四原则——档案已有的不问、长期不变的只在档案缺失时问一次、短期波动的确有需要才问、无必要给空数组。
- user 按三模式拼装：`FIRST`（首份：近 30 天明细 + 概要，指令侧重整体模式）/ `DAILY`（昨日明细 + 概要 + 近几天已给建议防重复）/ `BACKFILL`（缺口时段明细合并 + 回顾指令）；**双窗口概要**——「近30天概要」（近期模式，日常报告「相对常态变化」的参照）+「近90天长期概要」（长期习惯基线，习惯养成建议的依据；`AiDataSummarizer` 分别以 30/90 天窗口计算，统计量为聚合值 token 增量极小）；非空时追加**「用户档案（已知信息，勿再提问）」**与**「用户对此前追问的补充」**（已答未提交的问答）两段。
- 明细字段瘦身：只上分析必需字段（餐别/时间/食物/饭量/成分/类型/强度/总量），id 与录入时间不上行。
- `buildSentPayloadText()`：user 内容的美化排版——报告页「本次发送的数据」的数据来源（中文键让用户读得懂）。

### 提示词定制指引（想改 AI 行为从这里入手）

**首选：应用内定制**——设置 → AI 接口 → **提示词定制（高级）**：编辑框预填**完整** system 提示词（风格段 + 输出契约段），改完保存下一次报告即生效，「恢复默认」一键还原；定制内容随备份导出（换机带走）。**改动「输出要求」的 JSON 格式约定时，保存会被红色警告框拦截并要求二次确认**（`keepsContract()` 检测契约段是否完整保留）——契约被改坏后 AI 回复将无法拆解成板块，只能降级为原文保存，属于未知风险，故有此闸门。

**次选：改代码默认值**（对所有未定制用户生效的改动才需要动代码）。默认值由两段拼成：`buildDefaultStyleText()`（角色/导向/营养与提问原则）+ `buildContractText()`（JSON 报文契约，亦是二次确认的检测基准）：

| 想改什么 | 改哪里 |
|---|---|
| AI 的角色、语气、参照系（如换 Keto/素食视角） | `buildDefaultStyleText()` 的角色设定段 |
| 建议导向（习惯养成 vs 单日纠正的侧重） | 同上，「建议导向」段 |
| 营养品补充建议的给法（剂量口径、免责措辞） | 同上，「营养补充原则」段 |
| 追问行为（提问频率与审慎原则） | 同上，「提问原则」段 |
| 输出 JSON 契约（字段/字数/格式——**改动会影响二次确认基准，需与 AiReportParser/AiScreen 同步**） | `buildContractText()` |
| 喂给 AI 的数据范围与窗口（30/90 天概要、明细字段） | `buildUserMessage()`（明细段）与 `AiDataSummarizer`（概要段）、`AiReportGenerator` 的窗口常量 |
| 三种模式的指令措辞（首份/日常/补交） | `buildUserMessage()` 的「生成模式说明」 |

调参后无需迁移数据：新提示词只影响**下一次生成**的报告，历史报告按旧内容照常显示（建议条目缺新字段时界面自动隐藏对应行）。

## AiAnswers.kt —— 追问数据契约（0.4.1）

questionsJson / answersJson / 档案 JSON 三种结构的字段定义与宽容解析，生成器（写入端）与 AI 页（作答展示端）共用——字段语义只此一处说了算。要点：答案条目冗余存问题文本（作答与提交自包含）；`mergeProfileItem` 按 topic 覆盖实现档案更新。

## AiReportParser.kt —— 返回正文宽容拆解

剥 ```json 围栏 → 截首尾大括号 → 逐字段宽容读取（缺正文的建议条目跳过而非整体失败）。三段正文全空才判「不可解析」→ 生成器按 parseOk=false 原文保存降级展示。

## AiReportGenerator.kt —— 生成编排器

唯一入口，两个方法：`generateIfDue()`（条件触发：闹钟/自愈/懒检查用，配置齐全且昨日缺失才跑）与 `generateNow()`（手动：无视水位线，覆盖式重生成）。

核心机制：

| 机制 | 做法 | 为什么 |
|---|---|---|
| 成功才记账 | 水位线 `ai_last_report_epoch_day` 只在接口返回内容后推进 | 欠费/断网/超时/格式异常全部自然形成「缺口」，次日合并补交，零专门逻辑 |
| 模式判定 | 无水位线=FIRST；缺 1 天=DAILY；缺多天=BACKFILL | 一条 when 表达式，与提示词三模式一一对应 |
| 合并补交 | BACKFILL 一次请求带整个缺口时段（明细上限 14 天，更早只进概要） | 比逐日补 N 份快，营养分析本就更适合看周期 |
| 单飞锁 | `Mutex` 包住整个生成过程 | 闹钟/自愈/懒检查同时到点只跑一次 |
| 滚动清理 | 每次成功生成后删除 14 天窗口外的旧报告 | 报告是易逝文本，不是账本 |
| 追问记账（0.4.1） | 生成前收集档案 + 已答未提交问答随请求携带；**成功后**才标记提交日并把档案型并入个人档案；重新生成同日报告按问题文本保留旧答案 | 与水位线同哲学：失败不动账；用户的作答不因重生成而丢 |
| 尝试留痕 | 无论成败写 `ai_last_attempt_at`，失败写 `ai_last_error_text` | AI 页状态卡展示「上次为什么失败」 |

注意：**格式异常（parseOk=false）也推进水位线**——接口调用本身成功了，原文已存档，不该因模型偶发不守格式而阻塞次日流程；状态卡会提示「可重新生成」，手动重生成走 REPLACE 覆盖。
