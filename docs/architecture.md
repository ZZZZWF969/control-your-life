# 工程架构说明（面向项目所有者）

> 目的：让你随时能看懂工程分了几层、代码怎么协作、改哪里会影响哪里。
> 概念都用大白话解释；本文随结构性变化同步更新（项目维护约定）。
> 更新时间：2026-10-17（起床唤醒改双保险方案）

## 一、总览

单模块安卓应用（Kotlin + Jetpack Compose），代码全部在 `app/src/main/java/com/dailycontrol/app/` 下，按职责分四个包：

```
com.dailycontrol.app
├── DailyControlApp.kt   应用入口（进程启动时最先执行，注册通知渠道）
├── MainActivity.kt      唯一的界面容器（解析主题 → 挂载整个界面树）
├── data/                数据层：一切「存取」都在这
│   ├── entity/          表结构定义（饮食记录、运动记录、营养素行、餐别枚举）
│   ├── dao/             数据访问接口（增删改查的抽象声明，Room 自动实现）
│   ├── db/              数据库单例 + 版本迁移规则
│   └── settings/        应用设置仓库（DataStore：主题模式等轻量配置）
├── ui/                  界面层：一切「看得见」的都在这
│   ├── theme/           设计系统（颜色、形状——浅/深两套主题的定义处）
│   ├── components/      跨页面公共组件（时间选择弹窗、圆形徽标、确认弹窗）
│   └── screens/         五个页面 + 各自的表单/卡片
├── notify/              通知层：渠道注册与发送（三餐/背单词/规划/待办/起床五个业务渠道 + 通用）
├── backup/              备份协调层（2026-10-18 新增）：BackupManager——JSON 导出/恢复、
│                        每周自动备份到下载目录；它要同时指挥数据层与调度层，故独立成层
├── schedule/            调度层（第三阶段新增）：所有「定时」都在这
│   ├── ReminderScheduler  AlarmManager 精确排程封装（未授权精确闹钟时自动退化）
│   ├── ReminderReason     全部提醒类型的 requestCode 常量表（接收器按它分发）
│   ├── ReminderReceiver   到点接收器：按类型分发（询问/循环/规划/待办/起床）
│   ├── BootReceiver       开机重排（依赖「自启动」权限）
│   ├── DailyPlanner       每日提醒排程（三餐/规划时刻）+ 待办自愈重排
│   ├── VocabPlanner       背单词锚点制循环（10:00 起每 90 分钟，完成即滚明天）
│   ├── WakePlanner        渐进唤醒排程（N 声撤旧排新、存档 DataStore、重启自愈）
│   └── SystemAlarmSetter  起床闹钟写入系统时钟应用（SET_ALARM 协议；双保险方案下停用，保留备用）
└── util/                工具层：无状态底层工具（时间换算/格式化 + 系统时钟跳转封装）
```

数据层第三阶段的变化：`todo_task` 待办表（DB v4）；DataStore 新增提醒时刻、背单词包名/完成日期、最近规划日期等配置。

## 二、分层与调用关系

原则：**上层调用下层，下层不知道上层存在**。箭头方向不可反转。

```
界面层 ui/
   │  读写数据 / 读设置
   ▼
数据层 data/  ──(Room 框架)──►  SQLite 文件（应用私有目录）
   ▲
   │  读设置（主题）
MainActivity（容器）

通知层 notify/ ←── 界面层调用（设置页的自检按钮）
                 ←── 调度层调用（ReminderReceiver 到点时发送各类通知）

工具层 util/ ←── 谁需要谁调用（无状态、无副作用，最底层；ClockLinker 跳时钟被界面层与通知层共用）
```

一次典型调用的完整链路（以「保存一条饮食记录」为例）：

1. `RecordScreen`（记录页）打开 `DietEntrySheet`（录入表单）；
2. 用户点保存 → 表单把输入组装成 `DietRecord`（实体对象）回调给记录页；
3. 记录页在协程里调用 `db.withTransaction { dao.insert(...) }`（数据库事务）；
4. Room 把对象写进 SQLite，同时通知所有正在观察该数据的 Flow；
5. 记录页列表订阅着这个 Flow，数据库一变，界面自动刷新出新卡片——**界面不需要手动"刷新列表"**。

## 三、关键设计决策（为什么这样分）

| 决策 | 理由 |
|---|---|
| 数据库全局单例（`DailyControlDatabase.get()`） | 全应用共享一个连接，避免重复打开的开销与竞争 |
| DAO 只声明不实现（Room 编译期生成实现） | SQL 在编译期被检查，拼错列名直接构建失败而非运行崩溃 |
| 数据库版本迁移显式写在 `MIGRATION_x_y` | 升级不丢用户数据；schema 快照存档于 `app/schemas/` 可比对 |
| 记录与营养素明细同事务保存 | 要么全成功要么全不动，避免出现"有主记录没明细"的脏数据 |
| 餐别/营养素是独立实体类，界面卡片自己配颜色 | 数据层不掺界面概念，换 UI 不动数据库 |
| 时间统一存 epoch 毫秒，展示层才格式化 | 存储无时区歧义，显示随系统语言 |
| 主题与业务数据分离（DataStore vs Room） | 轻量配置与重数据各走各的通道，互不拖累 |

## 四、界面层的页面构成

| 页面 | 文件 | 内容 |
|---|---|---|
| 今日 | `TodayScreen.kt` | 只读汇总：三餐完成度、运动时长、当日列表、跳转记录页 |
| 记录 | `RecordScreen.kt` + `DietEntrySheet` / `DietRecordCard` / `ExerciseEntrySheet` / `ExerciseRecordCard` | 按日管理与增删改查 |
| 提醒 | `RemindScreen.kt` | 背单词状态卡、今日/明日待办清单（勾完成/删除）、去时钟开闹钟入口（有唤醒计划时）、规划入口 |
| 规划 | `PlanScreen.kt`（不在底栏，通知深链/提醒页进入） | 为今天或明天安排待办与起床唤醒；保存后引导去时钟开闹钟（双保险） |
| AI | `AiScreen.kt` | 占位（第四阶段） |
| 设置 | `SettingsScreen.kt` | 外观（主题三档）、提醒时间、跳转应用、链路自检与调试工具 |

底部导航在 `ui/AppRoot.kt`：它持有「当前在哪页」的状态，切换页面 = 交换界面树里的内容，五个页面互不直接引用（今日页跳记录页走的是导航路由，不是直接调用）。

## 五、未来扩展的挂点（规划中的层）

- **第三阶段 提醒系统**：新增调度能力（闹钟/定时），挂点在 `notify/`（通知发送已在位）+ 新的 `schedule/`（计划中：AlarmManager 调度、三餐/规划/背单词的规则存 Room 新表）；
- **第四阶段 AI**：新增网络层（OpenAI 兼容客户端 + API Key 存 DataStore），输入来自 data 层的汇总查询，输出为报告页；
- UI 精修专项（见 goal.md TODO）：只动 `ui/theme/` 与各页面样式，不碰数据层。
