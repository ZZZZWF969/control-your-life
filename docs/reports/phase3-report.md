## 三、过程中发现并解决的问题（按发现顺序）

1. **SET_ALARM 每日堆积**（用户真机反馈）：系统 API 只能新建不能读删时钟闹钟，自动写入必然冗余 → 全应用内渐进唤醒 → 仍嫌震动叫不醒 → 最终定为双保险方案（时钟手动开做主力、应用末声保底），SET_ALARM 代码保留备用。
2. **起床通知自第三阶段以来从未发出（重大隐藏 bug，模拟器实测逼出）**：接收器 when 分发中待办宽区间 4100..104099 排在前面，把旧起床码段 5000-5009 整段吞掉，起床分支成死代码——闹钟准点触发但按不存在的任务 id 静默跳过。修复：起床码段迁至 200000+、窄区间分支前置（env-pitfalls #18）。
3. **调试模拟踩坏真实排程**：模拟末声与真实末声共用 requestCode，PendingIntent 同码即同一闹钟，点模拟会把明早 08:00 末声搬到 30 秒后。修复：调试走独立码段 200101+。
4. **重启后起床类未恢复（真机测试 5 发现）**：根因非开机广播，而是两个规划页缺陷——起床选择不回填（重存默认「无课」默默清档）、保存「今天」连带撤销明天的唤醒。修复后补验通过。
5. 其余环境坑均已记入 docs/env-pitfalls.md（#16 渠道三件套、#17 force-stop 清闹钟/升级安装残留、#18 when 区间吞码段）。
